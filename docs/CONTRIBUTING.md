# Contributing Guide

Codyssey B2-2 팀의 협업 규칙입니다. **작업 시작 전에 한 번 읽고 시작하세요.**

규칙을 바꾸고 싶으면 이 문서를 고치는 PR을 올리면 됩니다. 다른 팀원 1명 이상 approve로 확정합니다.

---

## 1. 브랜치 전략 — GitHub Flow

| 브랜치 | 역할 |
|---|---|
| `main` | 항상 깨지지 않은 상태(문서 링크가 살아있고 예시 코드가 실행됨). 직접 push 금지, PR + approve 1명으로만 머지 |
| `<종류>/<깃헙아이디>-<주제>` | 작업 브랜치. 짧게 쓰고 머지하면 삭제 |

### GitHub Flow를 고른 이유 (3줄)

1. 브랜치가 `main`과 작업 브랜치 둘뿐이라 3명이 규칙을 헷갈리지 않고 지킬 수 있다.
2. 모든 변경이 PR을 거치니까 리뷰와 이슈 추적이 자연스럽게 강제된다.
3. 버전 릴리스가 없는 짧은 미션에 git-flow의 `develop`/`release`는 과하다.

### 지킬 것

- 작업 브랜치는 **항상 최신 main에서** 만든다 (`git checkout main && git pull origin main`)
- 브랜치 1개 = 이슈 1개 = PR 1개. 관련 없는 변경을 섞지 않는다
- `push --force`, main 히스토리 재작성은 팀 합의 없이 금지
- 머지되고 나면 로컬 브랜치도 지운다 (`git branch -d <브랜치>`)

## 2. 브랜치 이름 규칙

```
<종류>/<깃헙아이디>-<주제>
```

| 종류 | 언제 |
|---|---|
| `feature` | 예시 코드 추가 |
| `docs` | 노트·문서 작성 및 수정 |
| `fix` | 잘못된 내용 수정 |
| `chore` | 설정, 파일 이동·이름 변경 |

- 깃헙아이디는 소문자: `daeung-03`, `kimjexnghyexn`, `stevenkim18`
- 주제는 영어 소문자 + 하이픈, 3단어 이내

| ✅ | ❌ | 이유 |
|---|---|---|
| `docs/kimjexnghyexn-git-branch` | `test` | 누가 무슨 작업인지 모름 |
| `docs/stevenkim18-pr-review` | `stevenkim18` | 주제가 없음 |
| `feature/daeung-03-python-example` | `feature/새기능` | 한글·공백 금지 |
| `fix/stevenkim18-readme-link` | `fix2` | 번호로 구분하지 않음 |

## 3. 커밋 메시지 규칙

```
<타입>: <무엇을 어떻게 바꿨는지>
```

| 타입 | 언제 |
|---|---|
| `feat` | 기능·예시 코드 추가 |
| `fix` | 잘못된 내용 수정 |
| `docs` | 문서·노트 작성 및 수정 |
| `refactor` | 동작은 그대로 두고 구조만 정리 |
| `chore` | 설정, 파일 이동 같은 부수 작업 |

- 제목 50자 이내, 한글 OK, 마침표 없음
- **무엇을** 바꿨는지 대상이 보여야 한다
- 커밋 1개 = 의미 1개. 서로 다른 이유로 고친 파일들은 커밋을 나눈다

### 금지 — 의미 없는 메시지

아래에 걸리면 리뷰에서 **커밋 메시지 수정 요청**을 받습니다.

| 유형 | 예시 |
|---|---|
| 대상을 알 수 없는 단어만 | `update`, `fix`, `temp`, `wip`, `final`, `수정`, `ㅇㅇ` |
| 무엇을/왜 바꿨는지 없음 | `bug fix`, `edit file`, `파일 수정`, `코드 정리` |
| 커밋 내용과 다름 | 오타만 고쳤는데 `feat: 노트 추가` |

| ❌ | ✅ |
|---|---|
| `update` | `docs: 브랜치 노트에 HEAD 설명 추가` |
| `fix` | `fix: notes/README 목차 링크 경로 수정` |
| `wip` | `docs: 충돌 노트 초안 작성` |
| `파일 옮김` | `chore: 함수 노트 파일명 규칙에 맞게 변경` |

### push 전에 메시지를 잘못 쓴 걸 발견했다면

```bash
git commit --amend -m "docs: 올바른 메시지"
```

이미 push한 커밋에는 쓰지 않습니다. force push가 필요해져서 다른 사람 저장소와 어긋납니다.

## 4. 이슈 규칙

작업은 **먼저 이슈로 만듭니다.** Issues → New issue에서 종류를 고르세요.

| 양식 | 쓸 때 | 제목 프리픽스 |
|---|---|---|
| 📓 학습 노트 작성 | `notes/`에 노트 추가 | `docs:` |
| 📄 문서 작업 | README·CONTRIBUTING·SUBMISSION 수정 | `docs:` |
| ✨ 예시 코드 추가 | `src/`에 Python 예시 추가 | `feat:` |
| 🐞 수정 요청 | 잘못된 내용, 깨진 링크, 안 되는 코드 | `fix:` |
| 🔧 설정 · 구조 작업 | 저장소 설정, 파일 이동·이름 변경 | `chore:` |
| 💥 충돌 실습 | 의도적 충돌 만들고 해결·기록 | `docs:` |
| 🛠 트러블슈팅 실습 | amend/reset/revert/stash 실습·기록 | `docs:` |

- 제목 프리픽스는 양식이 자동으로 채워줍니다. 뒤에 내용만 쓰세요 (`docs: 브랜치 포인터 노트 작성`)
- 이슈에 **본인을 Assignee로** 지정하세요. 누가 뭘 잡고 있는지 보여야 겹치지 않습니다
- 이슈 번호를 PR 본문 `Closes #N`에 넣으면 머지될 때 이슈가 자동으로 닫힙니다

## 5. PR 규칙

- 제목: 커밋과 같은 형식 (`docs: 브랜치 노트 작성`)
- 본문 필수 항목 (`.github/pull_request_template.md`가 자동으로 띄워줍니다)
  - `Closes #이슈번호` — 이슈 없는 PR은 반려
  - **What** 변경 사항
  - **Why** 변경 이유
  - **How** 확인 방법
- 리뷰어 1명 지정
- 본인 PR은 본인이 approve할 수 없습니다 (GitHub이 막습니다). 반드시 다른 팀원에게 요청하세요

### 머지 조건

- [ ] approve 1명 이상
- [ ] 대화(conversation) 전부 resolve
- [ ] 머지 방식은 **Create a merge commit** — Squash·Rebase 금지 (브랜치 그래프가 제출 증빙이라서)
- [ ] 머지 후 원격 브랜치 삭제 (설정에서 자동으로 지워집니다)

### 크기

한 PR에 노트 1~2개. 크면 리뷰가 `LGTM`으로 흘러가고, 그건 이 미션에서 감점 요인입니다.

## 6. 코드 리뷰 규칙

### 최소 품질 기준

- **`LGTM`만 남기면 리뷰로 인정하지 않습니다.** 파일이나 줄을 근거로 한 코멘트 1개 이상 필수
- 작성자와 리뷰어 사이에 **최소 1번 주고받기**(답글 또는 반영 커밋)가 기록으로 남아야 합니다
- 각자 남의 PR에 **리뷰 2개 이상** 작성해야 합니다

### 코멘트 예시 4가지

| 종류 | 예시 |
|---|---|
| 질문 | "`git-branch.md` 24줄에서 브랜치가 파일이라고 하셨는데, `.git/refs/heads/` 열어본 결과도 같이 넣어줄 수 있나요?" |
| 대안 제안 | "`reset --hard` 예시를 먼저 보여주면 따라 하다 사고 날 수 있어요. `--soft` 먼저 설명하는 순서가 안전할 것 같습니다." |
| 리스크 지적 | "여기서 `push --force`를 소개하면 팀원이 공유 브랜치에서 쓸 수 있어요. 같은 블록에 금지 문구 넣어주세요." |
| 개선 제안 | "명령만 있고 결과가 없어요. `git log --oneline` 출력도 붙이면 나중에 재현이 됩니다." |

### 리뷰어

- 꼭 고쳐야 하는 건 `[must]`, 취향이면 `[nit]` 붙여서 구분합니다
- 사람이 아니라 문서를 지적합니다. "틀렸다"보다 "이렇게 하면 어떨까요"
- approve는 "이게 main에 들어가도 된다"는 서명입니다. 안 읽고 누르지 않습니다

### 작성자

- 모든 코멘트에 답합니다. 안 고칠 거면 이유를 답글로 남깁니다
- 리뷰 반영은 **새 커밋**으로 합니다. `amend` + force push하면 리뷰 맥락이 깨집니다
  - 예: `git commit -m "docs: 리뷰 반영 - git status 출력 추가"`

### 요청과 응답

- PR 올리면 팀 단톡방에 링크 공유
- 리뷰 요청받으면 **하루 안에** 응답 (못 볼 상황이면 단톡방에 미리 말하기)

## 7. 충돌 났을 때

```
충돌 발생
 → 단톡방에 바로 공유 (파일명 + 상대 브랜치)
 → 나중에 머지하는 쪽이 자기 브랜치에서 해결
 → 어느 쪽을 살릴지 상대와 합의
 → PR에 해결 요약 코멘트 남기기
 → docs/conflict-resolution.md 에 기록 (해결한 사람이 작성)
```

### 지킬 것

1. 혼자 판단해서 남의 작업을 지우지 않습니다. 어느 쪽을 살릴지는 상대와 합의합니다
2. 충돌 해결은 **자기 브랜치 안에서** 합니다. main에서 하지 않습니다
3. `--ours` / `--theirs`를 쓰기 전에 뭐가 ours인지 확인합니다 (merge 중에는 ours = 내 브랜치)
4. 겁나면 `git merge --abort`로 되돌리고 다시 시작합니다. 충돌 상태로 억지 커밋 금지
5. 기록에는 **마커 원문 + 어느 쪽을 왜 골랐는지 + 실행한 명령 + PR 링크**가 있어야 합니다

### 기본 명령

```bash
git pull origin main       # 충돌 발생
git status                 # 어떤 파일이 어떤 종류로 충돌했는지
git diff                   # 마커 확인 (기록용으로 복사해두기)
# 파일 고치고 마커 지우기
git add <고친 파일>
git commit
git push origin <내 브랜치>
```

되돌리기: `git merge --abort`

### 마커 읽는 법

```
<<<<<<< HEAD
내 브랜치 내용
=======
가져오는 쪽 내용
>>>>>>> origin/main
```

`modify/delete` 충돌(한쪽이 파일을 옮기거나 지운 경우)은 **파일 안에 마커가 생기지 않습니다.**
`git status`로만 확인되니, 충돌이 났다는데 마커가 안 보이면 `git status`를 읽어보세요.

## 8. 노트 작성 규칙

- 노트는 `notes/`에 두고, 파일명은 `notes/README.md` 목차에 적힌 이름을 그대로 씁니다
- 노트를 추가하면 **같은 PR에서** [notes/README.md](../notes/README.md) 목차에 한 줄 등록합니다
- 형식은 아래 5개 항목을 지킵니다

```markdown
# 제목
> 작성자: 이름 (@아이디) · 관련 이슈: #N

## 한 줄 요약
## 핵심 내용
## 직접 해본 것
## 헷갈렸던 점
## 참고 링크
```

- **`직접 해본 것`에는 실제로 실행한 명령과 출력을 넣습니다.** 남의 글 요약만 있는 노트는 반려합니다
- 분량 욕심내지 마세요. 짧아도 직접 해본 기록이 있는 쪽이 좋은 노트입니다
