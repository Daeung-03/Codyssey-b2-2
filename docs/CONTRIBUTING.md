## 1. 브랜치 전략 — GitHub Flow

| 브랜치 | 역할 |
|---|---|
| `main` | 항상 깨지지 않은 상태. 직접 push 금지, PR + approve 1명으로만 머지 |
| `<종류>/<깃헙아이디>-<주제>` | 작업 브랜치. 짧게 쓰고 머지하면 삭제 |

### GitHub Flow를 고른 이유 (3줄)

1. 브랜치가 `main`과 작업 브랜치 둘뿐이라 3명이 규칙을 헷갈리지 않고 지킬 수 있다.
2. 모든 변경이 PR을 거치니까 리뷰와 이슈 추적이 자연스럽게 강제된다.
3. 버전 릴리스가 없는 짧은 미션에 git-flow의 `develop`/`release`는 과하다.

### 지킬 것

- 작업 브랜치는 **항상 최신 main에서** 만든다 (`git checkout main && git pull origin main`)
- 브랜치 1개 = 이슈 1개 = PR 1개. 관련 없는 변경 섞지 않기
- `push --force`, main 히스토리 재작성은 팀 합의 없이 금지

## 2. 브랜치 이름 규칙

```
<종류>/<깃헙아이디>-<주제>
```

- 종류: `feature` `docs` `fix` `chore`
- 아이디: `daeung-03`, `kimjexnghyexn`, `stevenkim18`
- 주제: 영어 소문자 + 하이픈, 3단어 이내

| ✅ | ❌ |
|---|---|

| `feature/daeung-03-python-example` | `daeung` |
| `fix/stevenkim18-readme-link` | `feature/새기능` (한글·공백) |

## 3. 커밋 메시지 규칙

```
<타입>: <무엇을 어떻게 바꿨는지>
```

| 타입 | 언제 |
|---|---|
| `feat` | 기능·예시 코드 추가 |
| `fix` | 잘못된 내용 수정 |
| `docs` | 문서·노트 작성 및 수정 |
| `refactor` | 동작 그대로 두고 구조만 정리 |
| `chore` | 설정, 파일 이동 같은 부수 작업 |

- 제목 50자 이내, 한글 OK, 마침표 없음
- **무엇을** 바꿨는지 대상이 보여야 함

### 금지 — 의미 없는 메시지

| 유형 | 예시 |
|---|---|
| 대상을 알 수 없는 단어만 | `update`, `fix`, `temp`, `wip`, `final`, `수정` |
| 무엇을/왜 바꿨는지 없음 | `bug fix`, `edit file`, `파일 수정`, `코드 정리` |

| ❌ | ✅ |
|---|---|
| `update` | `docs: 브랜치 노트에 HEAD 설명 추가` |
| `fix` | `fix: notes/README 목차 링크 경로 수정` |
| `파일 옮김` | `chore: 함수 노트 파일명 규칙에 맞게 변경` |

push 안 한 최근 커밋 메시지는 `git commit --amend`로 고칩니다.

## 4. 이슈 · PR 규칙

### 이슈

- 작업은 **먼저 이슈로 만듭니다.** Issues → New issue에서 양식 선택
  - **작업** (`.github/ISSUE_TEMPLATE/task.md`) — 노트 작성, 문서 수정, 설정
  - **수정 요청** (`.github/ISSUE_TEMPLATE/bug.md`) — 잘못된 내용, 깨진 링크, 안 되는 예시 코드
- 제목은 커밋과 같은 형식 (`docs: 브랜치 포인터 노트 작성`)
- 이슈 번호를 PR 본문의 `Closes #N`에 넣어야 이슈가 자동으로 닫힙니다

### PR

- 제목: 커밋과 같은 형식 (`docs: 브랜치 노트 작성`)
- 본문 필수 항목 (`.github/pull_request_template.md`가 자동으로 띄워줍니다)
  - `Closes #이슈번호` — 이슈 없는 PR은 반려
  - **What** 변경 사항
  - **Why** 변경 이유
  - **How** 확인 방법
- 리뷰어 1명 지정
- 머지 조건: approve 1명 + 대화(conversation) 전부 resolve
- 머지 방식은 **Create a merge commit** (Squash 금지 — 브랜치 그래프가 증빙이라서)
- PR은 리뷰 가능한 크기로. 문서 기준 한 PR에 노트 1~2개

## 5. 코드 리뷰 규칙

- **`LGTM`만 남기면 리뷰로 인정 안 됩니다.** 파일이나 줄을 근거로 한 코멘트 1개 이상 필수
- 작성자와 리뷰어 사이에 최소 1번 주고받기(답글 또는 반영 커밋)가 남아야 함

### 코멘트 예시 4가지

| 종류 | 예시 |
|---|---|
| 질문 | "`git-branch.md` 24줄에서 브랜치가 파일이라고 하셨는데, `.git/refs/heads/` 열어본 결과도 같이 넣어줄 수 있나요?" |
| 대안 제안 | "`reset --hard` 예시를 먼저 보여주면 따라 하다 사고 날 수 있어요. `--soft` 먼저 설명하는 순서가 안전할 것 같습니다." |
| 리스크 지적 | "여기서 `push --force`를 소개하면 팀원이 공유 브랜치에서 쓸 수 있어요. 같은 블록에 금지 문구 넣어주세요." |
| 개선 제안 | "명령만 있고 결과가 없어요. `git log --oneline` 출력도 붙이면 나중에 재현이 됩니다." |

- 꼭 고쳐야 하는 건 `[must]`, 취향이면 `[nit]` 붙여서 구분
- 작성자는 모든 코멘트에 답합니다. 안 고칠 거면 이유를 답글로 남깁니다
- 리뷰 반영은 **새 커밋**으로.

## 6. 충돌 났을 때

```
충돌 발생
 → 단톡방에 바로 공유 (파일명 + 상대 브랜치)
 → 나중에 머지하는 쪽이 자기 브랜치에서 해결
 → 어느 쪽을 살릴지 상대와 합의
 → PR에 해결 요약 코멘트 남기기
 → docs/conflict-resolution.md 에 기록 (해결한 사람이 작성)
```

### 지킬 것

1. 혼자 판단해서 남의 코드 지우지 않기. 어느 쪽 살릴지는 상대랑 합의
2. 충돌 해결은 **자기 브랜치 안에서**. main에서 하지 않기
3. 겁나면 `git merge --abort`로 되돌리고 다시 시작. 충돌 상태로 억지 커밋 금지
4. 기록에는 **마커 원문 + 어느 쪽을 왜 골랐는지 + 실행한 명령 + PR 링크**가 있어야 함

### 기본 명령

```bash
git pull origin main       # 충돌 발생
git status                 # 어떤 파일이 충돌했는지
git diff                   # 마커 확인 (기록용으로 복사)
# 파일 고치고 마커 지우기
git add <고친 파일>
git commit
git push origin <내 브랜치>
```

되돌리기: `git merge --abort`

## 7. 노트 작성 규칙

- 노트는 `notes/`에, 형식은 [README 7번](../README.md#7-노트-내용-분배) 참고
- 노트를 추가하면 **같은 PR에서** [notes/README.md](../notes/README.md) 목차에 한 줄 등록
- 직접 실행한 명령과 결과를 꼭 넣기. 남의 글 요약만 있는 노트는 반려
